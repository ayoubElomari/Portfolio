# L'idée

<Lede>
  <Link to="/project/rendr">Rendr</Link> transforme un fichier JSON en vidéo
  sans que personne ne touche à une timeline. Audio Engine pose la même
  question côté son : mixage, ducking, égalisation, spatialisation, tout ça
  peut-il vivre dans la composition, au lieu d'être réglé à la main dans un
  DAW ?
</Lede>

Autant le dire clairement plutôt que de le cacher. <Link to="/project/rendr">Rendr</Link> est rapide parce que ses frames ne dépendent pas les unes des autres. On demande la frame 400, on obtient la frame 400, pas besoin de la 399 avant. L'audio ne joue pas ce jeu-là. Un compresseur a besoin d'anticiper ce qui arrive. La traîne d'une réverbération déborde sur les échantillons suivants. Rien de ce qui rend un traitement audio réellement professionnel n'est indépendant par nature.

Cette idée ne peut donc pas juste être « ajouter un moteur audio ». Une vraie question reste sans réponse. Est-ce que l'audio doit vivre dans le même runtime navigateur que le moteur vidéo, en gardant cette philosophie d'un seul code partout sur laquelle Rendr a été construit ? Ou est-ce qu'un vrai traitement audio impose de sortir de cette règle, avec un sous-processus dédié qui renvoie son résultat au navigateur en flux, pour l'édition ?

Les deux options tiennent la route. Aucune n'est gratuite. Garder le moteur d'un seul bloc, c'est se limiter à ce que permet l'API Web Audio. Le scinder en deux, c'est obtenir de vrais outils audio, le genre de traitement pour lequel un navigateur n'a jamais été pensé. Mais le moteur cesse alors d'être un seul runtime pour en devenir deux, qui se parlent à travers un flux.

Voilà où la réflexion s'arrête, pour l'instant.
